  The short version: right now the client refuses to listen to the server about stars and last-played, because listening would sometimes eat your own change before it got out the door.

----
The volume slider will feel different. It was raw linear amplitude (50% = −6 dB); it's now a cubic taper (50% ≈ −18 dB). That's the fix for "101 steps you can't hear apart", but it's a real change — one line in OutputStage.GainForVolumePercent if you want it gentler.
----
Lock-free synchronisation — correct in shape, but (A) is a bug in the
    protocol and (B) is a lock that reaches the RT thread anyway.

----
GC pauses / ArrayPool — the RT callback already allocates nothing;
    TrackDecoder.OnPlay's _scratch (:396-399) is grow-only and reused. The
    useful artifact here is a regression test asserting zero allocation.

----
Float internally: worth doing inside the render callback only. The ring
    should stay S16 — LibVLC 3.0's amem hardcodes S16N and never honours a
    requested fourcc (GaplessFormat.cs:9-18), so a float ring would store an
    exact widening of S16 at twice the memory for zero benefit.

----
long ring indices are read with Volatile.Read, which is not atomic on
   32-bit runtimes — Flower.Android still ships an armeabi-v7a

----
why is star a special case?
Library.TrackStarsChanged is a new event. SetStarred — both the Track Info window and Subsonic /star go through it — reached neither existing event, so a star would not have entered a starred-based playlist until something unrelated triggered a pass. It can't be folded into TrackStatsChanged: App.axaml.cs:740 forwards that to IPlayReporter, so a star raised there would be reported to the origin server as a listen. Checking the other two paths the doc had flagged went the other way — MergeReportedTrackState already raises TrackStatsChanged and MergeSyncedTracks already raises TracksUpdated, so both were covered.
----
Picture the desktop and the server, and the two things that happen on their own timers:

- The pull (catalog sync): "give me your whole library."
- The push (every five seconds): "here's what I know that you don't."

Now you star a song on the desktop. For a moment the desktop's answer is starred: true and the server's is still false. If the pull ran right then and took the server's answer for every track, it would set your star back to false — and then the push, comparing local against the baseline, sees nothing to report. Your star is gone, and nothing anywhere records that it ever existed. The pull would have raced the push and won.

So today the pull just doesn't touch those fields on a track it already knows. Nothing is ever lost, because the client's answer is never overwritten. The cost is the mirror image: the client also never learns anything about those fields. Star something on the server's web UI and your desktop won't hear about it.

With one admin device that's invisible. The desktop is the only thing that ever changes a star, information flows desktop → server, and both ends agree.

With two it stops converging. Star a song on the laptop; the server gets it; the desktop pulls and ignores it. Both machines are internally consistent and permanently disagree. Same for history — the server knows everything, but each machine only shows its own.

Why the fix isn't a one-liner. The client can't decide with two values; it needs three. It already keeps _knownServerState — "what the server told me last time" — so a pull could ask:

- Did the server's answer change since it last told me? → that's news, take it.
- Did mine drift from what the server told me? → that's my unpushed edit, keep it and push.
- Both changed? → someone has to lose, and I'd have to pick a rule.

That's a three-way merge, the same shape as git's: common ancestor, mine, theirs. Doable, but it means the baseline has to be trustworthy every time (including the moment between a pull landing and a push being acknowledged), the push and pull have to be ordered against each other, and each of those branches wants a test. Not something to bolt onto the end of this change — which is why I stopped where the behaviour is strictly "never loses data", named the gap, and left it as its own piece.
