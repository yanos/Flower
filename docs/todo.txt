1. The identity guard — and a second copy of it

Play() now compares _current.Track.Id instead of _currentPath == track.Path. While 
reading it I found SetUpcoming had the identical defect (_armedTrack.Path ==
next.Path), reached the same way — ArmUpcoming also goes through                   ResolveForPlaybackAsync, so every shuffle/repeat toggle mid-track tore down a decoder already seconds into decoding ahead and restarted its network fetch. Both fixed.

Two regression tests, in the streamed shape the old ones missed: same Track.Id, 
different signed URL. I verified them red first — reverting just the two comparisons
gives exactly 2 failures out of 23, and restoring gives 23/23.                  

2. CPU/memory instrumentation                                                   

Flower.Core/Diagnostics/ResourceMonitor.cs — resident memory, managed heap, CPU 
counts by generation, thread count. In Flower.Core so the server can use it.
                                                                                
Two things worth knowing:
- CPU comes from Environment.CpuUsage (.NET 9+); I probed it on this machine fir
  rather than assuming — busy-loop reads 100.0%, sleep reads 0.3%.
- Memory goes through mach task_info, not Environment.WorkingSet, on Apple platf
  WorkingSet returns 0 where the runtime has no implementation, and 0 is
  indistinguishable from a real answer on a settings screen. Verified against th
  Mac: 32MB resident, 32768MB device total.
                                                                                
ResourceMonitor is instantiable, not static, because CPU % is a delta — the settings
screen at 1s and the playback snapshot at 10s would otherwise eat each other's  
baseline. There's a test for exactly that.
                                                                                
Also added to the Playback snapshot log line: CpuPercent, ProcessMemoryMb,
ManagedHeapMb, Gen0/1/2, Threads — beside the decode counters, so "CPU pinned wh
the ring stayed full" is readable in one line.

4. AbruptFrames — I was wrong about this                                        

I need to correct what I told you earlier. I said MaxSampleDelta=32768 was "a full-scale jump — a click" and that those were "discontinuities in the PCM itself." That was overconfident.

The threshold is FLOWER_COREAUDIO_ABRUPT_SAMPLE_DELTA 24576 — 75% of full scale between adjacent samples. A full-scale sine at frequency f has a maximum adjacent delta of 32768 × 2sin(πf/48000), which reaches 24576 at about 5.9kHz. So any loud content above ~6kHz trips it legitimately, and cymbals and sibilance on a modern master do it constantly. 1–6 frames per 480,000 is ordinary percussion. There is no defect there to chase, and I've written that reasoning into impl.c next to the constant so it isn't misread again.

The real glitch evidence was the 1,153 dropped buffers, whose cause is fixed in item 1.

I also found a genuine problem while checking: those PCM-shape counters are computed in the vendored ma_on_output__coreaudio, which inspects only s16 and f32 buffers. Flower opens at s16 or s24. So on the phone I just switched to FFmpeg, all four counters will read 0 forever — and 0 reads as "found no discontinuities" when it means "never looked." They now print n/a instead. Closing it properly needs an s24 path in the native code and a rebuild of the vendored binaries; I did not do that.

One correction on my own process: I briefly concluded nothing called those functions at all, because I'd excluded vendor/ from the grep. The call sites are in native/miniaudio/vendor/miniaudio.h, and binary and source are in sync.

Nothing is committed. Worth testing on the phone first — particularly whether the FFmpeg façade loads at all on real hardware, which nothing has ever exercised.

why is star a special case?
Library.TrackStarsChanged is a new event. SetStarred — both the Track Info window and Subsonic /star go through it — reached neither existing event, so a star would not have entered a starred-based playlist until something unrelated triggered a pass. It can't be folded into TrackStatsChanged: App.axaml.cs:740 forwards that to IPlayReporter, so a star raised there would be reported to the origin server as a listen. Checking the other two paths the doc had flagged went the other way — MergeReportedTrackState already raises TrackStatsChanged and MergeSyncedTracks already raises TracksUpdated, so both were covered.
----
Picture the desktop and the server, and the two things that happen on their own timers:

- The pull (catalog sync): "give me your whole library."
- The push (every five seconds): "here's what I know that you don't."

Now you star a song on the desktop. For a moment the desktop's answer is starred: true and the server's is still false. If the pull ran right then and took the server's answer for every track, it would set your star back to false — and then the push, comparing local against the baseline, sees nothing to report. Your star is gone, and nothing anywhere records that it ever existed. The pull would have raced the push and won.

So today the pull just doesn't touch those fields on a track it already knows. Nothing is ever lost, because the client's answer is never overwritten. The cost is the mirror image: the client also never learns anything about those fields. Star something on the server's web UI and your desktop won't hear about it.

With one admin device that's invisible. The desktop is the only thing that ever changes a star, information flows desktop → server, and both ends agree.

With two it stops converging. Star a song on the laptop; the server gets it; the desktop pulls and ignores it. Both machines are internally consistent and permanently disagree. Same for history — the server knows everything, but each machine only shows its own.

Why the fix isn't a one-liner. The client can't decide with two values; it needs three. It already keeps _knownServerState — "what the server told me last time" — so a pull could ask:

- Did the server's answer change since it last told me? → that's news, take it.
- Did mine drift from what the server told me? → that's my unpushed edit, keep it and push.
- Both changed? → someone has to lose, and I'd have to pick a rule.

That's a three-way merge, the same shape as git's: common ancestor, mine, theirs. Doable, but it means the baseline has to be trustworthy every time (including the moment between a pull landing and a push being acknowledged), the push and pull have to be ordered against each other, and each of those branches wants a test. Not something to bolt onto the end of this change — which is why I stopped where the behaviour is strictly "never loses data", named the gap, and left it as its own piece.
