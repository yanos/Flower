Fixed
- Playlist reorder: the separate single-row path is gone at all three layers. Every drag, one row or several, now uses the multi-row code. A drop that leaves the visible order unchanged is still not an edit, as the single-row path already guaranteed.
- "nth copy of a song gets the nth entry id": one shared helper (CopiesBySong) replaces four hand-written copies in the playlist model, the merge and the queue.
- Repeated expressions: a playlist's content version and a wire row's song key are each written once now, instead of six and two times.
- Dead code:                                                                       - the forceInitiator switch and its election branch, which every caller bypassed;
  - the conflict event's unused Deletion field;                                    - the unused PlaylistSyncMapper.ResolveTracks;
  - a test-only NoteMoved overload;                                                - Track Info change notifications that nothing listens to.
- Efficiency:                                                                      - A sync session no longer rewrites the stored copy of every playlist that is
    already agreed at the same revision.                                           - Delete Local File removes a whole selection as one library edit, where it used to
    make one edit per song.                                                        - The merge's check for songs added at the end is linear instead of quadratic.
  - Startup builds the song-matching index only if some row needs it.              - The server no longer re-checks every playlist a second time after a push thatalready triggered the check.
  - Adding songs to a playlist no longer makes an extra trip to a background thread just to hand back its own input.
- Duplication: Track Info's clear button and TextInput's now share one ClearButton class.
- Comments: stale ones in Palylist.cs and elsewhere no longer say sync decides "did this change?" from UpdatedAt or by electing an initiator.

Skipped, because they are redesigns or change behaviour
- Rows carrying their entry id, which would replace the copy-counting in selection, slots and the queue. This is the deepest finding, and the biggest change.
- The queue's parallel origin list, which has to be updated by hand at about nine places.
- Moving the "a drop restores a removed song" rule out of the folder watcher. It runs inside the watcher's lock, and the watcher's tests rely on that.
- Smaller ones: one queue rebuild per row in a multi-row queue drag, a shared client for the playlist changes request, a single record for the conflict prompt's text, and skipping playlists whose rows didn't change on save.

Worth a /code-review. Three findings looked like real bugs, so I left them alone:
- When a sync session changes nothing but a Vibe Playlist's song pool, that pool is installed in place but never saved or shown.
- The /info playlists token still hashes UpdatedAt. An install that changes content without moving it gets a new revision, but devices aren't told to come back for it.
- The phone's Delete Local File warning doesn't use LocalFileDeletion, so it describes the user's own file differently from the desktop.
